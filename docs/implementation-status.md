# Sari-Fi implementation and migration notes

Implemented locally: same-SKU retail pricing, flat month-derived financing, exact centavo schedules, customer/POS previews and submitted snapshots, fresh checkout validation, admin catalog navigation, two-price editors, Cloudinary SDK delivery and browser uploads, the supplied owner portrait, a trusted checkout callable, and dry-run administrative tooling. Existing contracts are read from their saved snapshots.

## Configuration

Public browser settings are documented in `.env.example`. `@cloudinary/react` and `@cloudinary/url-gen` optimize approved product images with fit resizing, preserving the packaging. They do not upload files. The upload service posts only the file and unsigned preset; it never sends private credentials or falls back to Base64/Firebase Storage.

The `sarifi_demo_products` unsigned preset was created and verified in cloud `a5bi1hsj`, restricting formats and disallowing caller-chosen public IDs. The owner-requested demo catalog has 22 photos uploaded with the Node SDK. Local private account details are only in ignored `.env.local`; never copy that file or the supplied credential-bearing plan into version control. Rotate the exposed API secret as part of the account handoff.

The current local environment explicitly retains demo checkout compatibility (`VITE_ALLOW_DEMO_CHECKOUT=true`, `VITE_USE_TRUSTED_CHECKOUT=false`). Those client checks cannot secure a public payment system. Production should use the callable (`VITE_USE_TRUSTED_CHECKOUT=true`) after Firebase Auth migration, server-issued `role`/`customerId` claims, and RTDB Rules preventing direct financial writes/stock reservations. All existing client-side financial approval, settlement, cancellation and restock paths must be assessed with those Rules before deployment; do not deploy deny-write Rules blindly and break those workflows. No live Firebase Rules or functions were deployed.

`npm run build:functions` packages the trusted callable. It reserves the full checkout in one Admin SDK transaction and validates the same shared helpers on every retry. A root transaction is practical for the small demo; partition a reservation ledger before scaling. No callable is enabled automatically.

It needs active products from at least two suppliers and an eligible financing term. The three plan comparison screens follow the current configured terms. The main example uses `getUnitPrice`, `calculateFinancing`, `calculateCheckoutFinancing`, `planReservationPaths`, `resolveFinancialOrderStatus`, and `canTransitionOrder`. It creates supplier-specific demo contracts accepted by the real validator. Delivery follows Ready → Out for Delivery → Delivered → customer-confirmed Completed. Cash repayment stays pending until supervisor confirmation. GCash settlement is labeled as a simulator; principal release, remaining supplier credit and capped credit-limit growth match the application rules.

`WalkthroughAppProvider` is presentation-only: no subscriptions, reducers, authentication, or persistence effects. The underlying page content is inert while the guide controls remain usable, preventing the actual forms from submitting. Each frame is derived independently so jumping, Back, and replay cannot duplicate payments or stock changes. Exit/Escape discards the preview and reveals the original live session, whose subscriptions continue independently. No cleanup writes are required. The unused older modal with obsolete 5% financing and RTDB image-storage descriptions was removed.

The guide also has optional Voice on/off controls in both expanded and minimized views, plus Replay in the expanded guide. ## Catalog preparation

The 22 products from the owner's price-sheet image were added to the live `sari-fi-4806b` demo database on 19 October 2026 (Philippine time). The catalog was empty before seeding. Names and both explicit price columns were preserved, including Knorr's 5.76 and Coffee Mate's 4.00 regular prices. Existing supplier/category assignments were used. The owner authorized reasonable invented demo values: 60 units per product, reorder level 12, and estimated supplier cost at 85% of the lower retail price, rounded to centavos. These are demo estimates, not measured inventory or supplier quotations.

`data/price-sheet-seed.json` records the actual seeded item master, source product pages, original image URLs and SHA-256 checksums. All 22 downloaded images are in `data/product-images/`. Photos use representative flavors/packaging where the sheet omits those details; some show multipacks, while stock and the 12-unit pricing threshold count the product's individual sale unit. Photo rights were not independently verified. `data/price-sheet-photo-receipt.json` stores Cloudinary public IDs and delivery URLs; `data/price-sheet-seed-result.json` records the verified result. Do not infer verified weight, flavor, or image rights from the generic sheet names.

`npx tsx scripts/seedPriceSheetCatalog.ts` validates without writing; `--upload` uploads photos only; `--execute` creates missing products and inventory audit entries. It targets only this configured demo instance, verifies supplier/category references, checks the shared 11/12-unit pricing behavior, checks local image checksums, and uses conditional Firebase ETag writes to preserve concurrent catalog edits. Repeat execution skips existing products rather than resetting inventory or edits. Pre-write snapshots, intent, and result receipts are access-restricted outside the repository under `%LOCALAPPDATA%/SariFi/catalog-seed-backups`. This additive seed used the same RTDB access rules and product fields as the application; Firebase MCP was not connected.

`data/client-products-draft.csv` remains the original incomplete worksheet, not the seeded item master. The separate production-style CSV importer still requires completed review fields. Explicit prices must never be overwritten with derived prices.

`npm run catalog:review -- --csv data/client-products-draft.csv --out <new-review-file.json>` creates an image research worksheet with exact-match queries. It does not perform image search, download photos, infer licensing, or claim variants are matched. Research manufacturer/client sources, record candidates/rights, and review every image. After approval, `catalog:photos` reads local approved files and uploads with the Node-only SDK using `--execute --confirm-demo`; by default it validates without uploads. Per-image manifests retain public/asset IDs, source and reviewer. Use their verified URLs in the catalog CSV. Media deletion is intentionally not automatic.

## Controlled data migration

No privileged Firebase audit or destructive cleanup was executed. The additive demo seed above did not change suppliers, categories, accounts, settings, or financial records. The following separate migration tools require Application Default Credentials or a private `GOOGLE_APPLICATION_CREDENTIALS` file plus an exact `SARIFI_ADMIN_TARGETS` JSON allowlist of `{projectId,databaseURL,mode}` entries. Every connected migration command requires explicit `--project-id`, `--database-url` and `--mode staging|production`; never infer deletion authority from public Vite configuration.

1. Confirm the target and retained working accounts with its owner. Enable maintenance mode, isolate the tour, and arrange a verified server-side write freeze. Keep a secured copy of original Rules before freezing them.
2. `data:audit` inventories all root nodes, status counts, references and candidate demo IDs without modifying any records. `--backup --out <absolute-private-directory>` additionally saves full RTDB, Rules, Auth metadata, legacy Storage manifest and Cloudinary media inventory with checksums. Specify the legacy bucket or explicitly confirm that none exists. The output directory is access-restricted (including Windows ACLs).
3. Rehearse the backup with `data:restore-rehearsal -- --backup <file> --emulator-project demo-sarifi-restore-<unique> --out <private-directory> --execute` against a loopback RTDB emulator configured by `FIREBASE_DATABASE_EMULATOR_HOST`. It requires an empty namespace and produces a verified checksum receipt. This restores RTDB data for rehearsal, not Auth users or image bytes; the complete cross-service recovery rehearsal still needs operator verification.
4. Prepare a reviewed manifest following `scripts/lib/migrationSafety.ts`. It binds project, URL, mode, full snapshot hash, exact record hashes/paths, owner approval, separate actor/reviewer, verified backup and restore receipt. Ambiguous data stays retained. Reconcile reserved stock, active loans, open procurements and customer credit first; the tool blocks them rather than changing balances automatically.
5. `data:cleanup -- --manifest <file> ...target flags...` is a dry run. It reports exact counts, dependencies and blockers. Execution additionally needs `--execute --confirm "CLEANUP:<project>:<mode>:<database-host>" --out <private-directory>`, current hashes and verified deny-all browser write Rules. It deletes only reviewed leaf paths in one bounded atomic update and saves intent/result receipts externally. Root wipes, Auth deletes and media deletes are unsupported. Repeated execution fails closed as stale; use the receipt to verify the first run instead of resubmitting an old manifest. An interrupted network response is resolved with `data:verify` before any retry.
6. `data:verify` compares all surviving data with the backup, checks references and refuses success on anomalies. Production historical records should be archived/deactivated through catalog management, not deleted. The destructive tool permits only tightly scoped production test catalog records, retaining financial and identity records.
7. Only after successful verification, `catalog:import` accepts the reviewed CSV and exact cleanup receipt. It refuses existing SKU conflicts, merges missing categories and month-plan defaults, saves a pre-import snapshot, and verifies written paths. It does not wipe data. Review/sign-in/checkout/POS/restock flows in staging before restoring access.

These tools have pure unit tests for their preflight gates; a live/emulator backup, cleanup, interruption and restore rehearsal has not been executed in this workspace. Owner approvals in a document do not replace verification of the actual target or authorize unreviewed records.
